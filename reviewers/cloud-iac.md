# Cloud / IaC reviewer (AWS + GCP + Terraform)

Contract: every rule below is either a runnable check or a precise review question a
human can answer yes/no. No adjectives. No "follow best practices".

## Applies when
- Any `*.tf`/`*.tf.json` file exists in the repo.
- A `provider "aws"`, `provider "google"`, or `provider "google-beta"` block exists anywhere.
- `.terraform.lock.hcl` exists at a root/consuming module (not a reusable-module repo — see
  failure mode #11, reusable modules correctly do **not** commit this file).
- `AWSTemplateFormatVersion:` appears in a `*.yaml`/`*.json` (CloudFormation, covered lightly below).

## Blocking rules
| # | rule | how it is checked | failure it prevents |
|---|------|-------------------|---------------------|
| 1 | `terraform fmt`/`terraform validate` pass with no diff | `terraform fmt -check -recursive && terraform validate` exits 0 — **tested live** (`terraform 1.16.4`) — but note `validate` only warns, never fails, on deprecated-but-still-accepted arguments (see failure mode #12); treat a 0 exit as "syntactically valid," not "current" | malformed HCL, undeclared variables, or a provider-schema mismatch reaches `plan`/`apply` |
| 2 | No HIGH/CRITICAL misconfig in changed `.tf` files per `trivy config` | `trivy config --severity HIGH,CRITICAL --exit-code 1 .` — **tested live**: fires `AWS-0107` (SG open ingress), `AWS-0086/0087/0091/0093` (S3 public-access-block), `AWS-0080` (RDS unencrypted), `AWS-0180` (RDS publicly accessible) on a deliberately bad file | the classic exposure bugs (open SG, public bucket, unencrypted DB) reach `apply` |
| 3 | No failed `checkov` check tagged `IAM`/`Secrets`/`Networking` in changed files | `checkov -d . --check CKV_AWS_1,CKV_AWS_49,CKV_AWS_63,CKV_AWS_24,CKV_AWS_23,CKV_AWS_17,CKV_GCP_28,CKV_GCP_117,CKV_GCP_60 --compact` — **tested live**: all nine fire on deliberately bad AWS/GCP fixtures (below) | catches the one class `trivy config` provably misses on this stack — see failure mode #1 |
| 4 | `terraform plan` output is attached to the PR and read before merge, not just `apply`d from a laptop | review question: "is there a CI-generated `terraform plan -detailed-exitcode` output attached to this PR, or a `terraform_plan` PR comment (Atlantis/Terraform Cloud/a custom Action)?" | an unreviewed `apply` makes a destructive change (resource replacement, deletion) nobody read first |
| 5 | State backend declares locking (`use_lockfile = true` for S3 native locking, or a DynamoDB table for legacy S3 backends; GCS backend locks natively) — never a `local` backend for anything beyond a personal sandbox | `grep -n 'backend "local"' **/*.tf` should be empty outside a scratch/example directory; review the `backend` block's locking config directly | two concurrent `apply`s corrupt state or race-overwrite each other's changes |

## Common AI failure modes in this stack
| # | what the model does | why it looks right | detection | correct move |
|---|---------------------|--------------------|-----------|--------------|
| 1 | Writes an `aws_iam_policy`/`aws_iam_policy_document` with `Action: "*"`/`actions = ["*"]` and `Resource: "*"`/`resources = ["*"]` "to unblock" a permissions error while iterating | Every permission error disappears immediately, which reads as "the IAM is now correct" rather than "the IAM is now absent"; wildcard IAM is also the single most common copy-pasted StackOverflow/tutorial snippet | **tested, and the result is a real, non-obvious tooling gap**: `checkov -d .` fires `CKV_AWS_1`/`CKV_AWS_63` (jsonencode-inline form) or `CKV_AWS_49`/`CKV2_AWS_40` (`aws_iam_policy_document` data-source form — checkov uses **different check IDs for the same violation depending on which HCL shape expresses it**, confirmed by running both forms through checkov directly); **`trivy config` fires zero findings on either form** — its wildcard-IAM rule (`AWS-0057`/`AVD-AWS-0057`, `aws-iam-no-policy-wildcards`) exists in `trivy-checks` but is marked `deprecated: true` and scoped to `input: schema["cloud"]` (live AWS API scanning via `trivy aws`), not `schema["terraform"]` — it **never runs against Terraform source at all**, tested and confirmed empty on 0.74.0 with a current checks bundle. Relying on `trivy config` alone for Terraform IAM review misses this failure mode completely | write the exact action list and a scoped `Resource` ARN pattern; run **checkov specifically** for this class (not trivy alone); for GCP, the equivalent is binding `roles/editor`/`roles/owner` instead of a scoped predefined or custom role — see failure mode #7 |
| 2 | Creates an `aws_s3_bucket`/`google_storage_bucket` and stops, assuming the provider's default is private | **Tested, real, and this is the sharpest finding in this file**: `terraform-aws-modules/terraform-aws-s3-bucket@master:variables.tf:565-569` — `block_public_acls` defaults to `true` (a secure default) — **but** `variables.tf:184-197` — `server_side_encryption_configuration` defaults to `default = {}`, i.e. **encryption is opt-in even in the de-facto standard community S3 module**; a bucket built from the minimal example in that module's own README ships unencrypted unless the caller explicitly adds the encryption block | `trivy config` `AWS-0086/0087/0091/0093/0094` (public-access-block granularity, tested, all fire on a bucket resource with no `aws_s3_bucket_public_access_block`) and `AWS-0132` (no customer-managed KMS key) HIGH; `checkov` `CKV2_AWS_6` (public access block) and `CKV_AWS_145`(KMS)/`CKV_AWS_21`(versioning) — **tested live**, both fire; GCP equivalent: `checkov` `CKV_GCP_28` ("bucket is not anonymously or publicly accessible") and `CKV_GCP_29` ("uniform bucket-level access") — **tested live** on a `google_storage_bucket_iam_member` binding `role = "roles/storage.objectViewer", member = "allUsers"` | AWS: attach `aws_s3_bucket_public_access_block` with all four flags `true` **and** `aws_s3_bucket_server_side_encryption_configuration` — both are separate resources as of AWS provider v4+ (see failure mode #12), neither is inline on `aws_s3_bucket` anymore; GCP: never bind `allUsers`/`allAuthenticatedUsers`, and set `uniform_bucket_level_access = true` |
| 3 | Provisions an `aws_db_instance`/`google_sql_database_instance` and leaves storage encryption at its provider default | AWS: `terraform-aws-modules/terraform-aws-rds@master:variables.tf:36-40` — `storage_encrypted` defaults to `true` in the community module (a secure default the AI doesn't even need to set); **but the raw `aws_db_instance` resource's own provider default is `false`** — the safety only exists if you use the module, not the raw resource, which is exactly what an LLM asked to "just write the Terraform" tends to reach for. GCP has no equivalent toggle — Cloud SQL disk encryption is always-on by default (Google-managed key), which is a genuine asymmetry between the clouds worth knowing before assuming AWS's answer transfers | `trivy config` `AWS-0080` HIGH ("Instance does not have storage encryption enabled" — tested, fires only on the raw resource, not the module, confirming the module/resource gap above); `checkov` `CKV_AWS_16` | use the community module (`terraform-aws-modules/terraform-aws-rds`) rather than a raw `aws_db_instance` for exactly this reason — its defaults are safer than the provider's; if using the raw resource, set `storage_encrypted = true` explicitly, every time |
| 4 | Writes an `aws_security_group`/`google_compute_firewall` ingress rule with `cidr_blocks = ["0.0.0.0/0"]`/`source_ranges = ["0.0.0.0/0"]`, usually on port 22/3389/5432, "to make sure it's reachable" during setup | Works from literally any network immediately, which is exactly what makes initial testing painless and exactly what makes it dangerous left in place | `trivy config` `AWS-0107` HIGH ("unrestricted ingress from any IP address" — tested, fires specifically on port-22-shaped rules) and `AWS-0124`/`AWS-0099` (missing rule/SG description, LOW); `checkov` `CKV_AWS_24` ("no security groups allow ingress from 0.0.0.0:0 to port 22" — tested) and `CKV_AWS_23` (description) | scope `cidr_blocks` to a VPN/bastion CIDR or a specific known range; for genuinely public services (a public ALB on 443), that's a legitimate `0.0.0.0/0` — the review question is "does this port need to be open to the entire internet, or just to specific known callers," not a blanket ban |
| 5 | Provisions `aws_db_instance`/`google_sql_database_instance` with `publicly_accessible = true`/an enabled public IPv4, usually because the module's example snippet had it set that way for the tutorial's convenience | Removes an entire class of "can my app reach the DB" networking debugging during initial setup, at the cost of internet-exposing the database | **tested live, both clouds**: `trivy config` `AWS-0180` HIGH ("Instance has Public Access enabled") and `checkov` `CKV_AWS_17`; for GCP, `checkov` `CKV_GCP_60` ("Cloud SQL database does not have public IP") — and notably, `GoogleCloudPlatform/terraform-google-sql-db@main:modules/postgresql/variables.tf:336` — `ipv4_enabled` defaults to `true` in Google's **own** reference module, i.e. the official GCP Terraform module defaults to a public IP being provisioned unless the caller explicitly sets `ipv4_enabled = false` and configures `private_network` | set `publicly_accessible = false` (AWS) / `ipv4_enabled = false` + `private_network = <vpc self_link>` (GCP); connect via VPC peering/PrivateLink/Cloud SQL Auth Proxy, never a public endpoint, for anything holding real data |
| 6 | Leaves `backup_retention_period`/`backup_configuration` unset, assuming "the provider has a sane default" | The instance provisions successfully and works in every day-one test; backup gaps are invisible until the first data-loss incident, which by definition happens after this code shipped | **tested/verified from source, both clouds**: `terraform-aws-modules/terraform-aws-rds@master:variables.tf:319-323` — `backup_retention_period` defaults to `null` (defers to the AWS API default, which is a minimal 1-day window unless the engine specifies otherwise); `GoogleCloudPlatform/terraform-google-sql-db@main:modules/postgresql/variables.tf:285-291` — `backup_configuration.enabled` defaults to **`false`** in Google's own reference module — backups are opt-in even from the vendor's canonical module; `checkov` `CKV_AWS_233`/RDS backup checks, `trivy config` `AWS-0077` MEDIUM ("very low backup retention period" — tested) | set an explicit retention period (7-35 days depending on RPO needs) and, for RDS, `copy_tags_to_snapshot = true`; for Cloud SQL, `backup_configuration { enabled = true, point_in_time_recovery_enabled = true }` — neither cloud's module defaults get you this |
| 7 | Grants a GCP service account `roles/editor` (or, worse, `roles/owner`) at the project level "so it can do whatever it needs," instead of a scoped predefined or custom role | `roles/editor` makes every permission-denied error disappear at once, and it's the role every GCP quickstart tutorial grants the default compute service account | `checkov` `CKV_GCP_117` ("basic roles are not used at project level" — tested, fires on `google_project_iam_member`/`_binding` with `role = "roles/editor"`); `CKV_GCP_49` ("roles do not impersonate or manage Service Accounts used at project level") and `CKV_GCP_42` ("Service Account has no Admin privileges") are the narrower siblings; there is no AWS-side equivalent single-role antipattern this clean — the closest AWS parallel is the wildcard-action IAM policy in failure mode #1, which is why GCP gets a dedicated finding here and AWS doesn't repeat it | grant the narrowest predefined role that covers the actual API calls made (e.g. `roles/storage.objectAdmin` instead of `roles/editor` for a service that only touches GCS); if no predefined role fits, write a custom role with the exact permission list |
| 8 | Runs `terraform apply` directly (locally, or in a CI job with no gating step) with no prior `terraform plan` that a human read, especially on shared/production state | `apply` succeeds and reports "Apply complete!," which reads as success regardless of whether the changes it made were the ones intended — a `-/+` replacement (destroy+recreate) on a stateful resource looks identical in the CI log to a benign in-place update unless the plan was actually read first | review question: "is there a `terraform plan -detailed-exitcode`-produced plan visible in the PR (exit code 2 = changes present) before this was applied, and did a human read it — specifically checking for any `-/+` or bare `-` line on a stateful resource?"; **real CI pattern confirmed**: `terraform-aws-modules/terraform-aws-vpc@master:.github/workflows/pre-commit.yml` runs `terraform_validate` (via `pre-commit-terraform`) on every PR across both the module's min and max supported Terraform versions — validates syntax/types but **does not** run or post a `plan`, which is itself worth noting: even this widely-used module repo's CI stops at `validate`, not `plan` (expected, since it's a reusable module with no state of its own to plan against — the gap applies to *consumers*, not this repo) | gate merges on a posted `terraform plan` (Atlantis, Terraform Cloud/HCP, or a custom Action posting `terraform plan -detailed-exitcode` output as a PR comment); treat exit code 2 (changes present) as "needs a human read," not as a pass/fail signal by itself |
| 9 | Omits `lifecycle { prevent_destroy = true }` on stateful resources (databases, S3/GCS buckets holding real data), so a `terraform destroy`, a resource rename that Terraform interprets as delete+recreate, or an errant `-target` apply can silently delete data | Works identically with or without the block on every `plan`/`apply` that doesn't happen to touch that resource, so its absence is invisible until the one time it matters | `grep -rn "prevent_destroy" **/*.tf` — **tested absence**: zero matches in `terraform-aws-modules/terraform-aws-rds@master` and `terraform-google-modules/terraform-google-sql-db@main` — neither the AWS nor the GCP community module sets this itself (a deliberate, correct choice for a *reusable* module — the block is consumer-level policy, not something a shared module should hardcode for every user); the real gap is at the **consuming/root** configuration, not the module | add `lifecycle { prevent_destroy = true }` on the *consuming* project's stateful resources (not the module itself); combine with `deletion_protection = true` (AWS RDS/GCP Cloud SQL both support this as a **separate**, API-level flag from Terraform's own `prevent_destroy` — GCP in particular ships two distinct flags, `deletion_protection` (Terraform-level, defaults `true` in `terraform-google-sql-db`) and `deletion_protection_enabled` (API-level, across console/gcloud/API, defaults **`false`** — Terraform-level protection alone does not stop a `gcloud sql instances delete` run outside Terraform) |
| 10 | Adds tags/labels inconsistently — some resources get `Environment`/`Owner`/`CostCenter`, most don't, and there's no `default_tags`/enforced-labels mechanism | Individual resources with tags look "done" in a code review that reads one resource at a time; the gap (untagged resources) is only visible in aggregate, which a per-file PR review never shows | `checkov` `CKV_AWS_*` tagging checks / a custom `conftest`/OPA policy asserting every `resource` block of a taggable type has a non-empty `tags`/`labels` map — no single canonical rule ID exists across tools for "missing tags" the way there is for "public bucket," since taxonomy is org-specific; review question: "does the AWS provider block set `default_tags { tags = {...} }` (propagates to every resource automatically), or the GCP provider set a default-labels equivalent, so tagging isn't per-resource opt-in?" | set `provider "aws" { default_tags { tags = { ManagedBy = "terraform", Environment = var.environment } } } }` once at the provider level instead of per-resource; GCP has no direct `default_tags` provider-level equivalent — use a `locals.common_labels` map merged into every resource's `labels` argument, or a `conftest` policy that fails the plan if it's missing |
| 11 | Pins a module source to a branch (`?ref=main`) or omits `?ref=` entirely, and pins a provider with no version constraint (or a fully-open `>= 0`) | Works today, and updates "automatically" when the module/provider publishes a new version — which reads as low-maintenance rather than as "this build is not reproducible" | `tflint` rule `terraform_module_pinned_source` — **tested/confirmed as a real, currently-running check**: `terraform-aws-modules/terraform-aws-vpc@master:.pre-commit-config.yaml` scopes its `terraform_tflint` pre-commit hook to an explicit allowlist of rules including `terraform_module_pinned_source`, `terraform_required_version`, `terraform_required_providers` — run via `antonbabenko/pre-commit-terraform@v1.108.1` on every PR; also `checkov` `CKV_TF_1` (module source not pinned to a commit hash — checkov specifically wants a **hash**, not just any tag, which is stricter than tflint's check) | pin a module source to a full commit SHA or, at minimum, an exact semver tag (`?ref=v5.1.2`, never `?ref=main`); pin provider versions with a `~>` pessimistic constraint (`terraform-aws-modules/terraform-aws-vpc@master:versions.tf` uses `version = ">= 6.28"` — an open-ended floor, notably **not** a `~>` ceiling, which is itself worth a second look even in this reference repo) |
| 12 | Writes Terraform against the AWS provider using v3-era inline S3 bucket arguments (`acl`, `versioning {}`, `server_side_encryption_configuration {}` nested directly inside `resource "aws_s3_bucket"`), because that's the shape in most training-data-era tutorials and Stack Overflow answers | **Tested, and the result is more dangerous than a hard failure**: on a current AWS provider (v5.100.0), `terraform validate` does **not** fail on these — it exits 0 with only a `Warning: Argument is deprecated` (`server_side_encryption_configuration is deprecated. Use the aws_s3_bucket_server_side_encryption_configuration resource instead.`, tested verbatim), so this passes silently through any CI gate that treats `terraform validate` as pass/fail rather than reading its warnings | `terraform validate` exits 0 (confirmed live) — a warning, not a blocking failure, so it will **not** stop a merge on its own; `grep -rn "versioning {\|server_side_encryption_configuration {\|acl\s*=\|lifecycle_rule {\|cors_rule {" **/*.tf` inside an `aws_s3_bucket` resource block is what actually needs to gate this — **checkov does not catch it either** (tested: `CKV_AWS_21`, the versioning check, `PASSED` against the deprecated inline `versioning {enabled = true}` block exactly as it would against the standalone resource — checkov validates the resulting security posture, not which resource shape expresses it, so it is not a substitute for the grep here); confirmed via `hashicorp/terraform-provider-aws@main:CHANGELOG.md` that the v4 major deprecated these in favor of standalone `aws_s3_bucket_versioning`/`aws_s3_bucket_server_side_encryption_configuration`/etc. resources, and provider behavior (tested) is warn-and-continue, not warn-and-fail | never treat a clean `terraform validate` exit code alone as proof the HCL is current — read its warning output, or grep for the deprecated inline block names directly; use the separate standalone resources (`aws_s3_bucket_public_access_block`, `_versioning`, `_server_side_encryption_configuration`, `_lifecycle_configuration`) instead |
| 13 | Hardcodes a region (`region = "us-east-1"`) or an account ID (in an ARN string, a `condition` block, or a `provider` alias) directly in a shared/reusable `.tf` file instead of taking it as a variable or reading it from `data "aws_caller_identity"`/`data "aws_region"` | Works perfectly for the one account/region the author is testing against, and the hardcoding is invisible until the same code is applied to a second account/region (a second environment, a DR region, a second customer in a multi-tenant setup) | `grep -rnE '"[0-9]{12}"' **/*.tf` (bare 12-digit AWS account IDs) and `grep -rn 'region\s*=\s*"[a-z]{2}-[a-z]+-[0-9]"' **/*.tf` outside of a root `provider` block/variable default — a review-question flag, not a single named tool rule, since a hardcoded region in a *root* module's `provider` block is normal and correct, only a hardcoded value inside a *reusable module* or a resource-level `Resource`/`condition` string is the actual bug | use `data "aws_caller_identity".current.account_id` / `data "aws_region".current.name` instead of literal strings anywhere the value needs to be correct across accounts/regions; reusable modules should take region/account as input, never assume the deployer's own values |

## Edge cases routinely missed
| # | edge case | why it is missed | test that would catch it |
|---|-----------|------------------|--------------------------|
| 1 | A zone/AZ outage takes down every replica because `multi_az`/regional replication was never enabled — **tested default**: `terraform-aws-modules/terraform-aws-rds@master:variables.tf:221-225`, `multi_az` defaults to `false`; `terraform-aws-modules/terraform-aws-vpc@master:variables.tf:49-53`, `azs` defaults to an empty list (you must explicitly pass zones) and `one_nat_gateway_per_az` (`:1236-1240`) defaults to `false`, meaning a VPC spanning 3 AZs still routes all private-subnet egress through **one** NAT gateway in **one** AZ by default | day-one testing runs in a single AZ/region and never simulates an AZ failure, so nothing exercises the gap | `terraform plan` against `multi_az = true` and confirm cost/behavior is understood before enabling in prod; separately, chaos-test by blocking traffic to one AZ's NAT gateway and confirming other-AZ workloads keep working |
| 2 | Terraform state drift (someone changed a resource via the console/CLI, bypassing Terraform entirely) goes undetected until the next `apply` produces a surprising, large diff | No tool in this stack's default CI runs `terraform plan` on a schedule against already-applied state — it only runs on PRs that touch `.tf` files, so a console-made change with no corresponding PR is invisible indefinitely | schedule a periodic (e.g. nightly) `terraform plan -detailed-exitcode` job with no code change involved, alert if exit code is 2 (drift present) |
| 3 | A `terraform.tfvars`/`*.auto.tfvars` file with a real secret (an API key, a DB password passed as a variable default) gets committed because `.gitignore` only excludes `*.tfstate`, not tfvars | tfvars files are the normal, expected way to parameterize a module, so committing one reads as completing the setup, not leaking a secret | `git log --all --full-history -- '*.tfvars'` combined with a secret-scanner (`trivy fs --scanners secret .` / `gitleaks detect`) run over the full history, not just the current tree — a leaked secret in history stays leaked even after the file is later removed |
| 4 | `terraform.tfstate` itself (if ever run with a local/unencrypted remote backend) contains every resource's attributes **in plaintext**, including `aws_db_instance.password` and any other sensitive attribute, regardless of whether the source `.tf` marked the variable `sensitive = true` | `sensitive = true` only suppresses the value from CLI *output* (`plan`/`apply` logs) — it does not encrypt or omit the value from the state file itself, which is a common, reasonable-looking misunderstanding | confirm the state backend (S3 with SSE + a restrictive bucket policy, or Terraform Cloud/HCP) encrypts state at rest and restricts read access separately from write access — `grep -rn "sensitive = true"` in the repo tells you nothing about state-file exposure, only about CLI-log exposure |
| 5 | GCP/AWS service quota exhaustion (API rate limits, per-region resource count caps) breaks a `terraform apply` partway through, leaving state and real infrastructure out of sync (some resources created, the run failed before finishing) | Quotas are generous enough that dev/staging-scale applies never hit them; a large or fast-scaling prod apply is the first time the ceiling is found | `terraform plan` resource-count review before a large apply against known quota limits; `terraform apply` a large change in explicitly reviewed batches (`-target` deliberately, not accidentally) rather than one giant unreviewed apply |
| 6 | Log retention is left at its provider default — either unset (CloudWatch Logs default is **no expiration**, silently accumulating cost forever) or accidentally short (losing forensic value right when an incident needs it) | Both directions look identical in a `plan` diff (an unset `retention_in_days` argument), so neither the "costs too much forever" nor "deleted too soon" failure is visible without knowing the provider's specific default | `checkov` `CKV_AWS_338`(?)/log-group-retention checks — review question: "does every `aws_cloudwatch_log_group`/`google_logging_project_sink` set an explicit `retention_in_days`/retention policy matching a documented cost-vs-forensics decision, not the provider default?" |
| 7 | An autoscaling misconfiguration (no `max_size` ceiling on an ASG/MIG, or a scaling policy driven by a metric that spikes under retry storms) scales far past any reviewed cost budget before a human notices | `max_size` is set once at initial capacity planning and rarely revisited as a cost-control boundary, the same gap as the Kubernetes HPA failure mode in `reviewers/kubernetes.md` | review question: "is `max_size × largest instance type's hourly cost` a number someone explicitly approved, and does a budget alert exist independent of whether any single ASG respects its own ceiling?"; `infracost breakdown` against the plan surfaces the cost delta of a proposed `max_size` change before it's applied |
| 8 | A DNS record (Route53/Cloud DNS) change during a migration/cutover is applied, but the old record's TTL was left high, so traffic keeps hitting the old endpoint for the TTL duration after cutover, and the "rollback" of lowering TTL happens too late to help | Works fine in a test that doesn't wait out a real TTL window; the propagation delay only shows up in a real cutover under time pressure | lower TTL well in advance (hours to a day) of any planned cutover, confirm via `dig`/`terraform plan` that the low-TTL record is live before the actual cutover, not applied simultaneously with it |

## Approach selection
| decision | options | deciding factor | default recommendation |
|----------|---------|-----------------|------------------------|
| IaC tool | Terraform vs Pulumi vs AWS CDK vs CloudFormation | Terraform is cloud-agnostic (same tool for AWS+GCP+others) with the deepest module ecosystem (`terraform-aws-modules`/`terraform-google-modules` used throughout this file); CDK/CloudFormation are AWS-only but get first-class AWS support and drift-detection built into the console; Pulumi trades HCL for a real programming language (TS/Python/Go), which helps for complex conditional logic but fragments the ecosystem away from HCL-native tooling (`tflint`, `checkov`'s Terraform-specific checks, the module registry) | **Terraform** as the default — the tool this entire file's tested tooling (checkov, trivy config, tflint) is built around, and the only option here that's genuinely cloud-agnostic across AWS+GCP in one codebase; reach for **CDK** only if 100% AWS-only and the team is already TS/Python-fluent and wants compile-time type checking over HCL; avoid **CloudFormation** for new work (Terraform/CDK both have better module ecosystems); **Pulumi** only if a strong existing preference for real-language IaC outweighs losing HCL's tooling ecosystem |
| Module structure | one big root module vs environment-per-directory with shared modules | a single root module applied to multiple environments via workspaces risks a `terraform apply` in the wrong workspace context (typo'd `terraform workspace select`) touching prod by accident; separate directories per environment (`environments/staging/`, `environments/prod/`) make the blast radius of `cd environments/staging && terraform apply` explicit in the path itself | **separate directories per environment**, each with its own state/backend config, consuming shared modules from a `modules/` directory — Terraform workspaces are a footgun for anything where staging/prod divergence matters (different instance sizes, different `multi_az`, etc.), not just a naming convenience |
| Policy enforcement | checkov vs tfsec vs trivy config vs OPA/conftest, and which to run where | **tested, and this is the key finding of this file**: `trivy config` and `checkov` catch materially different, only partially-overlapping rule sets on the same input (confirmed: `trivy config` misses the IAM-wildcard class entirely — failure mode #1 — that `checkov` catches cleanly); `tfsec` is deprecated in favor of `trivy config` (confirmed via `tfsec`'s own CLI banner: "tfsec is joining the Trivy family... tfsec will continue to remain available for the time being, although our engineering attention will be directed at Trivy going forward") | run **both `trivy config` and `checkov`** in CI, not either alone — they are not redundant, per the tested gap above; use **conftest/OPA** only for org-specific policy (tagging conventions, naming standards) that neither off-the-shelf tool encodes; do not add **tfsec** to new CI — it's in maintenance mode, migrate any existing tfsec-only pipeline to `trivy config` |
| State backend | S3 (AWS) + native locking vs Terraform Cloud/HCP vs GCS (GCP) | a self-managed S3 backend needs its own locking (native `use_lockfile` on recent Terraform, or a DynamoDB table on older setups) and encryption configured explicitly; Terraform Cloud/HCP adds hosted state, locking, and a plan-review UI/API out of the box at the cost of a new external dependency; GCS backend locks natively with no extra resource needed | **S3 (with native locking) or GCS** for teams already fully in one cloud and comfortable owning the backend's encryption/access-policy config; **Terraform Cloud/HCP** once you want the plan-review-gate (Blocking rule #4) without building a custom CI Action for it — it directly solves the "was the plan read before apply" problem structurally rather than via convention |
| Drift handling | accept drift as normal vs scheduled drift-detection job vs `terraform import`-and-reconcile workflow | manual console changes will happen regardless of policy (an incident-response emergency fix, most commonly) — the choice is whether drift is *detected* promptly or discovered by surprise at the next unrelated apply | **scheduled drift-detection** (Edge case #2) as the default minimum; for teams with frequent emergency console changes, pair it with a documented "reconcile within 24h" process (`terraform import` or updating the `.tf` to match) rather than letting drift accumulate silently |
