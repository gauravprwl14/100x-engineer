# Kubernetes reviewer

Contract: every rule below is either a runnable check or a precise review question a
human can answer yes/no. No adjectives. No "follow best practices".

## Applies when
- Any file matches `apiVersion:` + `kind: (Deployment|StatefulSet|DaemonSet|Pod|Job|CronJob|Service|Ingress|HorizontalPodAutoscaler|NetworkPolicy)`.
- `Chart.yaml` exists anywhere in the repo (Helm chart).
- `kustomization.yaml` exists anywhere in the repo (Kustomize).
- `.github/workflows/*.yml` references `kubectl`, `helm upgrade`, or `argocd app sync`.

## Blocking rules
| # | rule | how it is checked | failure it prevents |
|---|------|-------------------|---------------------|
| 1 | Every rendered manifest is schema-valid against the target `kind`'s OpenAPI schema | `kubeconform -strict -summary $(find . -name '*.yaml')` exits 0 — **tested**: a `spec.replicas: "three"` (string instead of int) manifest fails with `jsonschema validation failed ... at '/spec/replicas': got string, want null or integer`, exit code 1 | a typo/wrong-type field an LLM introduced deploys nothing (apiserver rejects it) or silently no-ops depending on the field |
| 2 | No container in a rendered manifest has an unset or `:latest` image tag | `trivy config --severity MEDIUM,HIGH,CRITICAL .` has zero `KSV-0013` findings — **tested**: `image: nginx:latest` produces `KSV-0013 (MEDIUM): Image tag ":latest" used` | a redeploy of an unrelated pod (node reschedule, HPA scale-out) silently pulls a different image than what was reviewed |
| 3 | Every container sets `resources.requests` and `resources.limits` for both `cpu` and `memory` | `trivy config --severity LOW,MEDIUM,HIGH,CRITICAL .` has zero `KSV-0011`/`KSV-0015`/`KSV-0016`/`KSV-0018` findings — **tested**, all four fire independently on a bare container spec | one runaway pod exhausts node memory/CPU and evicts unrelated workloads on the same node |
| 4 | Every container sets `securityContext.runAsNonRoot: true`, `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false` | `trivy config .` has zero `KSV-0012`/`KSV-0014`/`KSV-0001`/`KSV-0118` findings — **tested**, `KSV-0118 "... is using the default security context, which allows root privileges"` fires on a container with no `securityContext` block at all | container breakout has a much larger blast radius (root on the node's kernel namespace, writable rootfs for planting a backdoor) |
| 5 | Every `Deployment`/`StatefulSet` with `replicas >= 2` has a matching `PodDisruptionBudget` | `kube-score score` has no `[CRITICAL] Deployment has PodDisruptionBudget` finding — **tested**, fires on any multi-replica Deployment with no PDB in the same file set | a routine node drain (upgrade, autoscaler scale-down) takes the whole service down instead of draining one replica at a time |
| 6 | A minimal conftest/OPA policy (below, in `## Verify`) passes on every changed manifest | `conftest test --policy policy/ <changed-files>` exits 0 | catches the five items above in one pass, diff-scoped, no extra tooling beyond what's already installed for CI |

## Common AI failure modes in this stack
| # | what the model does | why it looks right | detection | correct move |
|---|---------------------|--------------------|-----------|--------------|
| 1 | Omits `resources.requests`/`resources.limits`, or sets `limits == requests` on every container by reflex regardless of workload shape | The manifest deploys and runs fine in a lightly-loaded dev cluster; `limits==requests` is a copy-pasted "best practice" that reads as safe | `trivy config` `KSV-0011`/`KSV-0015`/`KSV-0016`/`KSV-0018` (tested, fire independently per field); **real counter-evidence to the reflex**: `prometheus-operator/kube-prometheus@799f3d73b:manifests/prometheusOperator-deployment.yaml` sets `requests: {cpu: 100m, memory: 100Mi}` / `limits: {cpu: 200m, memory: 200Mi}` (2x headroom, not equal), and `manifests/alertmanager-alertmanager.yaml` requests `cpu: 4m` against a `100m` limit (25x gap) — bursty, low-baseline workloads get equal limits==requests only when the workload's actual variance is unknown; **also real, the opposite failure**: `argoproj/argo-cd@f1a052174:manifests/base/{repo-server,application-controller,server,redis}/*.yaml` sets **zero** resources on any core component (`grep -c "resources:"` = 0 across all four base Deployments) — the reference install of a widely-run production GitOps controller ships with no requests/limits at all | set `requests` to the workload's steady-state P50, `limits` to a multiple of that based on observed burst (not 1x) or leave `limits` unset for CPU (CPU limits cause throttling, not OOM, so many teams set memory limits only, plus a CPU request); never set both by copy-paste without looking at real usage |
| 2 | Tags images `:latest`, or omits a tag entirely (implicit `:latest`) | Works in every dev iteration since `imagePullPolicy` defaults to `Always` for `:latest`, so the newest build is always picked up locally | `trivy config` `KSV-0013` (tested); gatekeeper-library `library/general/disallowedtags` (`K8sDisallowedTags`, sample `container-image-must-not-have-latest-tag`); kyverno `best-practices-vpol/disallow-latest-tag/disallow-latest-tag.yaml` (CEL: `!container.image.endsWith(':latest')`); **real violation, still present**: `argoproj/argo-cd@f1a052174:manifests/base/repo-server/argocd-repo-server-deployment.yaml:22` — `image: quay.io/argoproj/argocd:latest` — and the same string appears 5 times in the fully-rendered `manifests/install.yaml` that gets `kubectl apply`'d in production, confirmed live with `trivy config` (`KSV-0013 MEDIUM`) | pin to an immutable digest (`image@sha256:...`) or a semver tag your CI produced; a mutable tag lets a node reschedule silently run different code than what was reviewed |
| 3 | Ships no `livenessProbe`/`readinessProbe`, or sets a `livenessProbe` with tight `initialDelaySeconds`/`failureThreshold` that restarts a pod still warming up (JIT warmup, cache fill, large dataset load) | Passes local `kubectl run` smoke tests where startup is instant; the aggressive liveness probe "looks" more correct because it fails fast on genuine deadlocks | `kube-score score` flags missing probes directly (tested); **absence, checked directly**: neither gatekeeper-library, kyverno/policies, kubescape/regolibrary, nor trivy-checks (332 `.rego` files under `checks/kubernetes/`, zero matches for probe-timing) has any rule that catches an *aggressive* liveness probe — only presence/absence of probes is mechanically checkable, not their timing correctness; this is a review-only gap | use a dedicated `startupProbe` (generous `failureThreshold × periodSeconds`) to cover slow first-boot, and give `livenessProbe` a `failureThreshold` wide enough that only a genuinely wedged process trips it — `readinessProbe` should be the tight, fast-failing one since it only removes the pod from Service endpoints, not kills it |
| 4 | Leaves `securityContext` unset, or sets it at the container level but not the pod level (or vice versa) | Container-level `runAsNonRoot`/`readOnlyRootFilesystem` look complete in a diff review; the pod-level default (root, writable) is invisible unless you check both scopes | `trivy config` `KSV-0118` ("using the default security context, which allows root privileges") fires specifically on the *pod-level* gap even when the container level is set — **tested live**: `argoproj/argo-cd@f1a052174:manifests/base/repo-server/argocd-repo-server-deployment.yaml` sets `runAsNonRoot`/`readOnlyRootFilesystem`/`allowPrivilegeEscalation: false`/`capabilities.drop: [ALL]` at container level but has no pod-level `spec.template.spec.securityContext`, and `trivy config` on that file produces the exact `KSV-0118` finding; gatekeeper-library ships four separate templates for this (`pod-security-policy/{privileged-containers,users,allow-privilege-escalation,read-only-root-filesystem}`) rather than one, because each is independently bypassable | set both pod-level (`runAsNonRoot`, `runAsUser`, `fsGroup`, `seccompProfile.type: RuntimeDefault`) and container-level (`allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, `capabilities.drop: [ALL]`) — see `prometheus-operator/kube-prometheus@799f3d73b:manifests/prometheusOperator-deployment.yaml` for a manifest that sets all of both |
| 5 | Puts a secret value directly in `env: [{name: X, value: "..."}]`, or commits a `kind: Secret` with `data:` populated from a hand-run `base64` command | `type: Opaque` + base64 "looks" encrypted to a reviewer who doesn't know base64 is trivially reversible, and the diff renders as unreadable gibberish, which reads as "handled" | `trivy config` `KSV-0109` ("ConfigMap with secrets" — regex-pattern secret-in-value detection, covers the ConfigMap case but not a literal Secret's `data:` since that's expected there) plus a generic secret-scanner (`trivy fs --scanners secret .` or `gitleaks detect`) run over the whole diff, since `trivy config`'s k8s misconfig checks (the `KSV-*` set) do not scan literal string values for entropy/secret-shape outside ConfigMaps specifically — **this is a real, tested gap**: no `KSV-*` rule matches a hardcoded token in a Deployment's `env.value`; you need the secret-scanning subsystem, not the misconfig subsystem, for that half of the problem | use `envFrom.secretRef` sourced from a Secret populated by External Secrets Operator/Sealed Secrets/a CSI driver (see Approach selection), never a literal `value:`; never commit a real `Secret` manifest — base64 is encoding, not encryption |
| 6 | Ships a multi-replica `Deployment` with no `PodDisruptionBudget` | The Deployment's own `replicas: N` reads as sufficient redundancy; a PDB is an extra object that doesn't affect whether the app runs today | `kube-score score` `[CRITICAL] Deployment has PodDisruptionBudget` (tested); **real absence, verified with grep**: `argoproj/argo-cd@f1a052174` — zero `PodDisruptionBudget` objects anywhere in the repo (base, ha, or any install.yaml variant) despite the project documenting an HA mode; **real presence**: `prometheus-operator/kube-prometheus@799f3d73b:manifests/{prometheus,alertmanager,prometheusAdapter}-podDisruptionBudget.yaml`, each `minAvailable: 1`; gatekeeper-library's `K8sPodDisruptionBudget` constraint additionally checks `maxUnavailable != 0` and `minAvailable < replicas` — a PDB that blocks all voluntary disruption is as bad as none | add a PDB with `minAvailable: 1` (or `maxUnavailable: 1` for large replica counts) for every workload that can't tolerate simultaneous unavailability; a PDB with `minAvailable == replicas` blocks node drains entirely — that's a different bug, not a fix |
| 7 | Ships multiple replicas with no `podAntiAffinity`/`topologySpreadConstraints`, so the scheduler is free to co-locate all of them on one node | The Deployment "has 3 replicas" and reads as HA; co-location is invisible until the one node holding all three goes down | review question: "does `kubectl get pods -o wide` for this workload show replicas spread across >=2 nodes/zones, or could the scheduler legally put them all on one?"; kyverno `other-vpol/topologyspreadconstraints-policy` requires spread only once `replicas >= 3` (via `matchConditions`) — a real, citable threshold for when to bother; **real absence**: `prometheus-operator/kube-prometheus@799f3d73b:manifests/prometheus-prometheus.yaml` runs `replicas: 2` with zero anti-affinity/topology-spread set anywhere in the repo's own resources (the fields exist only in the CRD's *schema*, exposed to users, never populated by the project itself) | add `topologySpreadConstraints` (preferred over `podAntiAffinity` — it's zone-aware and doesn't hard-fail scheduling by default) keyed on `topology.kubernetes.io/zone` and `kubernetes.io/hostname` once `replicas >= 2`; `whenUnsatisfiable: ScheduleAnyway` for small clusters that can't guarantee spread capacity |
| 8 | Sets `hostNetwork: true` or mounts a `hostPath` volume "to make debugging easier" or to access a node-local resource, and leaves it in the manifest after debugging | Both work immediately and unblock whatever the model was trying to access (a node port, a local socket); neither breaks anything in a single-tenant dev cluster | `trivy config` `KSV-0009` (host network) / `KSV-0023` (hostPath); kubescape distinguishes `C-0048` (hostPath mount) from `C-0045` (*writable* hostPath mount) — the writable case is strictly worse and worth a separate gate; gatekeeper-library `pod-security-policy/{host-network-ports,host-filesystem}` | `hostNetwork`/`hostPath` should not appear in application workload manifests at all outside a small, named allowlist of node-agent DaemonSets (CNI, log shippers, CSI drivers) that genuinely need node-level access — treat every other occurrence as a review-blocking finding |
| 9 | Ships a namespace with services talking to each other over ClusterIP with no `NetworkPolicy`, relying on namespace/cluster boundaries alone | The CNI allows all pod-to-pod traffic by default, so nothing breaks; a NetworkPolicy is "extra" work with no functional payoff until an incident | **default-allow is not a probe-detectable gap per-file** — a review question instead: "does this namespace have at least one default-deny `NetworkPolicy` (`podSelector: {}`, `policyTypes: [Ingress, Egress]`)?"; kyverno's `best-practices-gpol/add-network-policy` (a `GeneratingPolicy`) auto-creates exactly that default-deny policy on every new Namespace, which is the strongest citable pattern found — enforcement by generation, not just validation; `cilium/cilium@f9bbe7996:examples/policies/l3/egress-default-deny/egress-default-deny.yaml` and `examples/kubernetes/servicemesh/policy/default-deny.yaml` (a clusterwide default-deny except kube-dns) are real `CiliumNetworkPolicy` templates; **nuance**: even `prometheus-operator/kube-prometheus@799f3d73b:manifests/prometheus-networkPolicy.yaml` — a security-conscious project's own policy — sets `egress: [{}]` (allow-all egress), restricting ingress only; full default-deny-both-directions is rare even among examples meant to demonstrate the practice | default-deny both `Ingress` and `Egress` per namespace, then explicitly allow the specific pod-to-pod and pod-to-external flows the app needs; if egress can't be fully locked down yet, lock down ingress first — it's the higher-value half and the one every reviewed example actually does |
| 10 | Creates a `ServiceAccount`, binds it to `cluster-admin` via a `ClusterRoleBinding` "to avoid RBAC errors while iterating," and never narrows it afterward | `cluster-admin` makes every permission error disappear immediately, which reads as "the RBAC is now correct" rather than "the RBAC is now absent" | review question: "does `kubectl get clusterrolebinding -o json \| jq '.items[] | select(.roleRef.name=="cluster-admin") | .subjects'` include this ServiceAccount, and if so, is there a written reason?"; kyverno `other-vpol/restrict-binding-clusteradmin` (CEL: `object.roleRef.name != 'cluster-admin'`) plus the sibling `other-vpol/block-cluster-admin-from-ns`; kubescape `C-0261` ("ServiceAccount token mounted") and `C-0035` (named "Administrative Roles" in-source — not literally "cluster-admin-binding" despite what the filename suggests, so cite the control's actual title, not its filename); gatekeeper-library has no cluster-admin-specific template (confirmed absent — its closest control is `automount-serviceaccount-token`, a different, narrower concern) | scope a `Role`/`ClusterRole` to the exact verbs+resources the workload needs; set `automountServiceAccountToken: false` on any pod that doesn't call the Kubernetes API at all (`argoproj/argo-cd@f1a052174:manifests/base/repo-server/argocd-repo-server-deployment.yaml:19` does exactly this for its repo-server, which never calls the k8s API) |
| 11 | Omits `terminationGracePeriodSeconds` (defaults to 30s) and any `preStop` hook on a workload whose in-flight requests or connection drains genuinely take longer than 30s | The default is silent — nothing errors, the pod just gets SIGKILLed at 30s during every rolling deploy, and in a low-traffic dev environment no request is ever mid-flight when that happens | review question: "what is this app's real p99 request/shutdown time, and is `terminationGracePeriodSeconds` set to comfortably more than that?"; **real, still-live citable pattern**: `kubernetes/examples@d6b8cd27e:databases/cassandra/cassandra-statefulset.yaml` sets `terminationGracePeriodSeconds: 1800` (30 minutes) paired with a `lifecycle.preStop.exec.command` that runs `nodetool drain` before the process receives SIGTERM — a real worked example of grace-period sized to the actual drain operation, not the default; **absence**: neither `argo-cd` nor `kube-prometheus` sets `terminationGracePeriodSeconds`/`preStop` on any of their own Deployments/StatefulSets | set `terminationGracePeriodSeconds` to (max expected in-flight duration + buffer), and add a `preStop` hook that stops accepting new work (deregister from Service/LB) before the process is sent SIGTERM — the two together, not either alone |
| 12 | Wires an `HorizontalPodAutoscaler` to `averageUtilization` on CPU for a workload that's actually memory-bound, I/O-bound, or queue-depth-bound (worker pulling from SQS/Kafka) | CPU is the only metric that works with zero extra setup (`metrics-server` is usually already present; a custom-metrics adapter is not), so it's the path of least resistance regardless of what actually predicts load | review question: "does the thing this HPA scales on (CPU) correlate with the thing that actually determines whether more replicas help (queue depth, request latency, memory)?"; **absence, verified across three real production repos**: `grep -rl "kind: HorizontalPodAutoscaler"` returns zero results in `argoproj/argo-cd`, `prometheus-operator/kube-prometheus`, and `cilium/cilium` (manifests, not vendored Go source) — none of three widely-run infra projects ships an HPA example at all, custom-metric or otherwise, which is itself worth knowing before citing "just look at a real HPA" as advice | for a worker consuming from a queue, scale on queue depth via `external.metrics.k8s.io` (KEDA is the common path to this today) instead of CPU; CPU-based HPA is correct only when CPU genuinely is the bottleneck resource for that specific workload |
| 13 | Changes a mounted `ConfigMap`'s data and expects the running pods to pick it up, or expects a `kubectl apply` on the ConfigMap alone to trigger a rollout | A ConfigMap update via `kubectl apply` succeeds with `configured` in the output, which reads as "done"; the actual pods keep running the old, already-loaded config until they happen to restart for an unrelated reason | review question: "does this Deployment's pod template annotation include a hash of the ConfigMap/Secret content it mounts, so a content change forces a new `spec.template` and therefore a rollout?"; real, widely-deployed pattern: `grafana-community/helm-charts@0c6f07c1:charts/grafana/templates/deployment.yaml:39-48` sets `checksum/config: {{ include "grafana.configData" . | sha256sum }}` (plus separate checksums for dashboards-config, sc-dashboard-provider-config, secret, and secret-env) as a pod template annotation — any content change changes the hash, which changes the pod template, which triggers a normal rolling update through the Deployment controller, no separate restart mechanism needed | add a `checksum/config` (or per-object) annotation computed from the ConfigMap/Secret content under `spec.template.metadata.annotations`; for values that don't need a full rollout, mount the ConfigMap as a volume (kubelet syncs volume-mounted ConfigMaps automatically, typically within ~1 minute) instead of `envFrom`, which never updates without a pod restart regardless |
| 14 | Defaults to `Deployment` for anything with a database/queue/cache inside it, because that's the workload kind used for everything else in the same PR | `Deployment` is the more commonly generated kind (it's what most tutorials scaffold), and for a single-replica dev instance it "works" identically to a StatefulSet | review question: "does this workload need a stable network identity (predictable pod DNS name) or stable per-replica storage (a distinct PVC per replica that survives pod rescheduling)? If yes to either, it needs a `StatefulSet`, not a `Deployment`."; no policy-engine rule encodes this decision (checked gatekeeper-library, kyverno/policies, kubescape/regolibrary, trivy-checks — none has a StatefulSet-vs-Deployment rule; this is a design-judgment gap, not a tooling gap) — `SOURCE: original` for the review question itself | use `StatefulSet` for anything where "which specific replica has this data" matters (databases, anything doing leader election with identity, Kafka/Cassandra-style clustered storage); `Deployment` for anything stateless where replicas are interchangeable |
| 15 | Runs `kubectl apply -f generated.yaml` directly against a cluster (own machine or CI) with no diff step, trusting that the generator (Helm template, kustomize build, or hand-edit) produced what was intended | `kubectl apply` succeeds and returns `configured`/`unchanged` per object with no indication of *what* changed vs. the live cluster state, so a large accidental diff (e.g. a templating bug that regenerated every object's labels) looks identical to a clean apply | review question: "was `kubectl diff -f <file>` (or `helm diff upgrade`, or an ArgoCD/Flux dry-run diff) run and read before this applied?" `kubectl diff` requires no extra tooling beyond the `kubectl` binary already present — `SOURCE: original`, no repo in the reviewed set documents this as a named CI gate, but the command itself is a stock `kubectl` subcommand, not an invention | run `kubectl diff -f <manifests>` (exit 1 if there's a diff, by design — treat non-zero as "review this, don't auto-apply") before `kubectl apply`, or route all applies through GitOps (ArgoCD/Flux) whose UI/PR diff *is* the review step — see Approach selection |

## Edge cases routinely missed
| # | edge case | why it is missed | test that would catch it |
|---|-----------|------------------|--------------------------|
| 1 | Node drain (upgrade, spot reclaim, autoscaler scale-down) during an active deploy evicts pods faster than the new ones become Ready, causing a capacity dip | Single-replica dev/staging clusters never trigger a real drain; CI never simulates one | `kubectl drain <node> --ignore-daemonsets` against a staging node mid-rollout, assert request success rate doesn't dip below the PDB's guaranteed minimum |
| 2 | Image pull fails or is rate-limited (Docker Hub anonymous-pull limits, registry outage) mid-rollout, and the new ReplicaSet gets stuck at `ImagePullBackOff` with no automatic rollback | Works every time in CI/dev where the registry is fast and un-throttled, and most registries used in CI have authenticated (higher-limit) pulls | pull from an intentionally rate-limited/unauthenticated registry path in a staging pipeline; assert the Deployment's `progressDeadlineSeconds` is set (so a stuck rollout is flagged, not silently half-deployed forever) |
| 3 | Cluster autoscaler cold-start: a scale-out event takes 1-3+ minutes (new node boot, CNI/kubelet ready) that the HPA/PDB math didn't budget for, so pods queue in `Pending` during exactly the traffic spike that triggered the scale-out | Load tests against an already-warm, over-provisioned cluster never exercise the scale-from-zero-extra-capacity path | load test that starts from a cluster at its autoscaler floor and ramps traffic fast enough to force a scale-out; assert p99 latency during the node-boot window, not just after |
| 4 | A `PersistentVolumeClaim` resize (`spec.resources.requests.storage` increased) is a no-op for the running pod until the pod restarts (for most non-`Retain`, non-online-resize storage classes), and some CSI drivers don't support expansion at all | The `PVC` object itself updates immediately (`kubectl get pvc` shows the new size), which reads as "resized," while the filesystem inside the running container is still the old size | check `StorageClass.allowVolumeExpansion: true` before relying on this at all; after a resize, exec into the pod and confirm `df -h` matches the new PVC size, not just `kubectl get pvc` |
| 5 | A rollback of an application deploy whose current schema migration is not backward-compatible (a column the old code needs was already dropped by the new code's migration) breaks immediately on rollback | Rollback is tested as "does the old container image start," not "does the old container image work against the *current* database schema" | before any migration that drops/renames, deploy N+1's migration first (expand), then N+1's code, confirm N's code still runs against the expanded schema, only then contract in N+2 — test the rollback path specifically, not just the forward path |
| 6 | No client timeout on calls between in-cluster services means one slow/wedged downstream Pod exhausts the caller's connection pool/event loop, cascading the failure upstream through the whole call chain | Works under any load test that doesn't include a deliberately slow/hanging downstream, which most load tests don't simulate | inject artificial latency (a `tc netem` sidecar, or a mock that hangs) on one downstream call and confirm the caller degrades (sheds load, times out, circuit-breaks) rather than exhausting its own resources |
| 7 | All replicas restart simultaneously (a `ConfigMap`/`Secret` rollout, a node-pool-wide upgrade) and hit a cold cache/connection-pool/JIT-warmup wall at the same instant, creating a thundering-herd spike on the datastore they all depend on | A single-pod restart never exposes this; it only appears when every replica cold-starts in the same few seconds | force a full simultaneous restart (`kubectl rollout restart` with `maxUnavailable` temporarily raised) against a staging datastore under realistic connection limits, watch for connection-pool exhaustion or thundering-herd query spikes |
| 8 | Clock skew between nodes (NTP drift, especially on self-managed clusters without `chrony`/NTP daemonsets enforced) breaks anything relying on wall-clock ordering across pods — JWT `exp` validation, distributed lock TTLs, log correlation | Every managed-cloud node pool (EKS/GKE/AKS) ships NTP by default, so this only bites self-managed clusters, which most teams don't test against | `kubectl exec` into pods on different nodes, compare `date -u` output; assert a monitoring alert exists for node clock drift beyond a threshold (a few hundred ms) |
| 9 | A `ResourceQuota`/`LimitRange` on the namespace silently rejects new pods once the quota is hit, and the failure surfaces as a scheduling error in `kubectl describe`, not in application logs or the deploy pipeline's own output | The deploy pipeline (`kubectl apply`/`helm upgrade`) reports success because the *object* was created and accepted; only the *pod* fails to schedule, one layer down from what the pipeline checks | after every deploy, assert `kubectl get pods -n <ns>` shows the expected replica count actually `Running`, not just that `kubectl apply`/`helm upgrade` exited 0 |
| 10 | An HPA with no `maxReplicas` ceiling appropriate to the cluster's real capacity, combined with a metric that spikes under a retry storm or a DDoS-shaped traffic pattern, scales out far enough to blow through a cloud cost budget or exhaust cluster capacity entirely | `maxReplicas` is usually set once, early, based on expected steady-state load, and never revisited as a cost-control boundary | review question: "is `HorizontalPodAutoscaler.spec.maxReplicas × (per-pod cost)` an amount someone has explicitly approved, and is there a cluster-level `ResourceQuota` backstopping it regardless of what any single HPA requests?" |

## Approach selection
| decision | options | deciding factor | default recommendation |
|----------|---------|-----------------|------------------------|
| Manifest authoring | Helm vs Kustomize vs plain manifests vs jsonnet | Helm packages+versions+templates for distribution to others; Kustomize is base+overlay patching of manifests *you* own, with no templating language to learn; jsonnet is a manifest-*generation* library/DSL — `prometheus-operator/kube-prometheus@799f3d73b` states this explicitly: "The content of this project is written in jsonnet... This project could both be described as a package as well as a library," i.e. jsonnet earns its complexity when you're building a reusable manifest-generation platform, not deploying one app; `argoproj/argo-cd@f1a052174:manifests/base/kustomization.yaml` uses plain Kustomize base+overlay (resources list, image name/tag overrides) for its own install manifests | **Kustomize** for manifests you own and deploy via GitOps (no templating footguns, diffable overlays); **Helm** the moment you're consuming a third party's chart or need to distribute your own app to others with configurable values; reach for **jsonnet** only if you're building a manifest-generation library used by many teams, not for a single app's deploy config; avoid **plain unlayered manifests** past ~5 objects — you lose environment-overlay capability |
| GitOps vs CI-push | ArgoCD vs Flux vs `kubectl apply`/`helm upgrade` from CI | ArgoCD ships a UI, app-of-apps pattern, and a visible sync-status/diff surface non-platform-engineers can read; Flux is more minimal, Kustomize-native, and has no UI of its own (usually paired with Weave GitOps or Grafana for visibility); CI-push (`kubectl apply` in a pipeline) has zero extra infrastructure but no drift detection — cluster state can diverge from git with nothing catching it | **ArgoCD** once you have more than ~1 team deploying to the cluster or need drift detection + an audit trail non-engineers can read; **CI-push** is a reasonable default for a solo/small-team single-service repo where the extra ArgoCD/Flux control-plane isn't worth operating yet; pick **Flux** over ArgoCD specifically when you're already all-in on Kustomize and don't want a UI/control-plane to operate |
| Secrets | External Secrets Operator vs Sealed Secrets vs cloud-native CSI driver vs SOPS | ESO syncs from an external secret store (AWS/GCP/Vault) *into* a k8s `Secret` continuously — best when secrets are already centrally managed and multiple clusters/clouds need them; the cloud-native Secrets Store CSI driver mounts the cloud secret store's values directly as a volume, no k8s `Secret` object created at all — best when you're single-cloud and want to avoid k8s `Secret` etcd storage entirely; Sealed Secrets encrypts a `Secret` so it's safe to commit to git, decrypted only by the in-cluster controller — best when you want zero external secret-store dependency; SOPS encrypts files (not just k8s `Secret`s) with support for multiple KMS backends, decrypted at apply-time via a `kustomize`/`helm` plugin | **cloud-native CSI driver** (AWS/GCP Secrets Manager CSI) if you're single-cloud and already paying for that cloud's secret manager — least moving parts; **External Secrets Operator** the moment you're multi-cloud or need the value materialized as an actual k8s `Secret` for other tooling to consume; avoid **Sealed Secrets**/**SOPS** unless you specifically need secrets committed to git with no external service dependency (air-gapped/regulated environments) |
| Ingress | nginx-ingress vs Traefik vs cloud load balancer (ALB/GCLB Ingress) vs Gateway API | nginx-ingress has the broadest documentation/community base and works identically across clouds; a cloud-native Ingress (AWS Load Balancer Controller, GCE Ingress) integrates tightest with that cloud's LB features (WAF, target groups) at the cost of portability; Gateway API is the upstream-standardized successor with explicit role separation (infra team owns `Gateway`, app teams own `HTTPRoute`) and is where new features land first going forward | **nginx-ingress** as the default for portability and documentation depth on a new project; move to **Gateway API** (via any conformant implementation, including Cilium's or nginx's own Gateway API support) once you have multiple teams that need independently-owned routing config, or need protocols/features (gRPC, TCP/UDP routing, traffic splitting) the `Ingress` API can't express; use the **cloud-native Ingress** only when you specifically need a cloud-proprietary LB feature (e.g. AWS WAF attached directly) |
| Service mesh | none vs Istio vs Linkerd vs Cilium's built-in mesh | a mesh's mTLS/L7-observability value only exceeds its operational cost once you have enough east-west traffic complexity (many services, multiple teams, a genuine need for per-hop mTLS beyond what NetworkPolicy gives you) that the sidecar/control-plane overhead pays for itself; a separate mesh control plane (Istio/Linkerd) run alongside a CNI you don't already have deep in is two systems to operate | **no mesh** is the default — NetworkPolicy (default-deny, see failure mode #9) plus mTLS at the application/ingress layer covers most teams' actual needs without a second control plane; if you do need one, prefer **Cilium's built-in service mesh** (you already run Cilium as CNI — no second control plane) over adding **Istio**/**Linkerd** as an independent system, unless you specifically need a feature only they provide |
| Database | managed (RDS/Cloud SQL) vs self-hosted in-cluster (via an operator: CloudNativePG, Zalando's postgres-operator, etc.) | a managed DB offloads backup/patching/failover/replication to the cloud provider; a self-hosted-in-cluster DB gives full control and can be cheaper at very large scale, but multiplies operational surface (you now own PVC resize edge cases, StatefulSet failover, backup verification) | **managed** (RDS/Cloud SQL) by default, always — the operational cost of self-hosting a stateful database inside k8s is rarely worth it below "dedicated platform team with a specific reason" scale (data residency, extreme cost pressure at scale, or a workload the managed offering genuinely can't support) |
| Manifest repo layout | manifests co-located in each service's repo vs a single separate GitOps repo | co-located manifests keep app code and its deploy config in one PR/review, which is simpler below a handful of services; a single GitOps repo gives one place to see the whole cluster's desired state and is what ArgoCD's app-of-apps pattern assumes | **co-located in the service repo** below ~3 services (fewer repos to keep in sync); **a single separate GitOps repo** with per-environment overlays once you have more than ~3 services or multiple teams — ArgoCD/Flux both expect and work best against this shape |
| Managed Kubernetes | EKS vs GKE vs AKS vs self-managed (kubeadm/kOps) | data gravity (where your other infra already lives) dominates this decision far more than K8s-specific feature differences; GKE Autopilot removes the most node-management burden (no node pool sizing/patching at all) of the three major clouds; self-managed buys full control at the cost of owning control-plane upgrades, etcd, and CNI/CSI wiring yourself | **whichever cloud your other infrastructure (VPC, IAM, data stores) already lives in** — cross-cloud K8s for its own sake adds networking/IAM friction with no corresponding benefit; **GKE Autopilot** specifically if starting fresh with no strong node-management requirements; **self-managed** only with a dedicated platform team and a concrete reason (on-prem, air-gapped, regulatory) |
