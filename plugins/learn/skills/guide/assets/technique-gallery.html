Three rules that apply to every technique
  • One strong visual per idea beats five weak ones.
  • Every diagram or widget gets 2–4 "reading this" notes: what shapes mean, what to notice, what to try.
  • Static first: facts inside a widget must also appear as text.

The URL-shortener facts used throughout: 100M new URLs/month, 100:1 reads, ~40 writes/s, ~4,000 reads/s (20,000 at peak), 3 TB over 5 years, base62 × 7 ≈ 3.5 trillion keys, key service, 302 for analytics, Redis for hot links.

1 · Structure

Structure techniques

In 10 secondsShow how the parts of a topic relate before diving into any one part.

In-10-seconds box

What it is: A highlighted box at the top of a page that states the whole point in one or two sentences.

What it does for the reader

  • Lets a skimming reader get the answer without reading the page.
  • Tells a careful reader what the rest of the page will prove.
Best forOpening every page with the whole point
Avoid whenNever — use it everywhere
FormatsAll formats (Markdown: blockquote)

Example: The URL shortener's entire design in one sentence.

In 10 secondsEstimate first, generate keys with a key service, cache hot links, redirect with 302 to keep analytics.
How to read it
  • Read it first. If it answers your question, you can skip the page.

How to build it: A bordered block with a small label ('In 10 seconds') and 1–2 sentences. Markdown: a blockquote.

Concept map (metro style)

What it is: A map of the whole topic drawn like a subway map: each coloured line is a category, each station is a topic.

What it does for the reader

  • Shows everything the guide covers on one screen.
  • Shows the reading order inside each category.
  • Doubles as navigation — click a station to open it.
Best forHome page overview of 3–9 categories
Avoid whenFewer than ~5 topics — a list is enough
FormatsHTML/SVG · React · Mermaid

Example: Three categories of the URL shortener (requirements, design, operations) and their topics.

How to read it
  • Pick a line (category), read its stations left to right.
  • Stations further right build on earlier ones.
Notes on this example
  • Each line is a category; stations are topics in reading order.
  • Clicking a station opens that page in a real guide.

How to build it: SVG built from a list of categories and topics; one horizontal line per category, a circle per topic. Markdown: Mermaid flowchart with subgraphs.

Mind map (radial)

What it is: One central idea with its sub-topics radiating outward like spokes.

What it does for the reader

  • Shows that the sub-topics are peers — no order, no hierarchy.
  • Good for a quick 'what are all the parts?' overview.
Best forOne topic with many branches of equal weight
Avoid whenBranches with an order — use flow
FormatsHTML/SVG · React · Mermaid

Example: The six aspects of a URL shortener: keys, redirects, storage, cache, analytics, capacity.

How to read it
  • Start at the centre; each spoke is one independent aspect.
  • Colour groups related spokes.
Notes on this example
  • Centre = topic; colour = category (blue sizing, teal design, green ops, violet data).
  • No order implied — radial layout says 'these are peers'.

How to build it: SVG: centre ellipse, nodes placed around a circle. Markdown: Mermaid mindmap.

Tree / hierarchy

What it is: A top-down diagram where each item splits into its parts.

What it does for the reader

  • Shows what contains what.
  • Makes the size of each branch visible at a glance.
Best forTaxonomies, component breakdowns
Avoid whenRelations that cross branches — use a concept map
FormatsHTML/SVG · React · Mermaid

Example: The system split into write path, read path and async work, each with its components.

How to read it
  • Read top to bottom: a box's children are the parts it is made of.
  • Siblings on the same level are alternatives or parallel parts.
Notes on this example
  • Read top-down: parent contains children.
  • Keep to 3 levels; collapse deeper ones.

How to build it: SVG boxes with connecting lines, max 3 levels. Markdown: nested bullet list or Mermaid flowchart TD.

2 · Process & time

Process and time techniques

In 10 secondsShow order: what happens first, who does what, what changes state.

Flow (boxes + arrows)

What it is: A row of boxes joined by arrows, where each box is one step and the arrow means 'then'.

What it does for the reader

  • Shows a process in the order it happens.
  • Makes it obvious which step depends on which.
Best for3–6 step processes with one actor
Avoid whenBranching logic — use a decision tree
FormatsHTML · Mermaid flowchart LR · numbered list

Example: Creating a short link: submit → get a code → save → return the short URL.

1. Submitlong URL
→
2. Codefrom key service
→
3. SaveKV store
→
4. Returnshort URL
How to read it
  • Read left to right.
  • Each box causes or enables the next one.
Notes on this example
  • Read left to right; each box causes the next.
  • One actor only — several actors need a swimlane.

How to build it: HTML flex row of step boxes with arrow characters between them. Markdown: Mermaid flowchart LR.

Sequence diagram (step-through)

What it is: A diagram with one vertical line per participant (person or system) and horizontal arrows for each message between them, in time order from top to bottom.

What it does for the reader

  • Shows who talks to whom, and in what order.
  • Reveals round trips, waiting and hidden dependencies.
  • The step-through buttons let readers follow one message at a time.
Best forMessages between systems or people
Avoid whenA single actor — use flow
FormatsHTML/SVG · Mermaid sequenceDiagram

Example: A browser opening a short link: API checks Redis, falls back to the KV store, answers with a 302.

  • Static text: hot links are served from Redis (≈20% of links, 80% of traffic); misses read the KV store; the answer is a 302.
How to read it
  • Column headers are the participants; the dashed lines under them are their 'lifelines'.
  • Each arrow is one message; read them top to bottom.
  • Press Next to highlight one step and read why it happens.
Notes on this example
  • Columns are participants; arrows run top to bottom in time.
  • Step notes explain why each message exists — and are repeated as static text below.

How to build it: SVG generated from a list of [from, to, label, note] steps plus Back/Next state. Markdown: Mermaid sequenceDiagram (static).

Swimlane

What it is: A process diagram split into horizontal rows ('lanes'), one per role, team or system. Each step sits in the lane of whoever does it.

What it does for the reader

  • Shows who is responsible for each step, not just the order.
  • Makes hand-offs between roles visible (a step moving to another lane is a hand-off).
  • Exposes work that happens separately or later, such as async jobs.
Best forWork split across roles or services
Avoid whenOne role — use flow
FormatsHTML/SVG · React · Mermaid

Example: Creating and sharing a link: the user submits, the API server takes a code, the key service refills its batch, analytics count clicks later in their own lane.

How to read it
  • Each row is one actor; its name is on the left.
  • Numbered cards show the order across all lanes.
  • When consecutive cards jump lanes, work is handed off.
Notes on this example
  • One row per role; numbered cards show order.
  • The analytics lane runs later and separately — async work is easy to spot.

How to build it: SVG: one coloured band per lane, step cards placed by lane (row) and order (column). Markdown: Mermaid flowchart with one subgraph per lane, or a table (step · lane).

State machine

What it is: A diagram of the states something can be in and the events that move it from one state to another.

What it does for the reader

  • Shows every allowed status and every allowed change.
  • Makes missing or illegal transitions easy to spot.
Best forLifecycles with named states
Avoid whenContinuous values — use a chart
FormatsHTML/SVG · Mermaid stateDiagram-v2

Example: The life of a short code: reserved → assigned → active, disabled after abuse, re-activated after appeal.

How to read it
  • Each rounded box is a state (a status the thing can have).
  • Each arrow is a transition, labelled with the event that triggers it.
  • No arrow between two states means that change is not allowed.
Notes on this example
  • Boxes are states; arrows are transitions labelled with their trigger.
  • Illustrative lifecycle for a short code.

How to build it: SVG boxes and labelled arrows. Markdown: Mermaid stateDiagram-v2.

Timeline

What it is: A vertical or horizontal line with events placed in time order.

What it does for the reader

  • Shows what happened when, and how long things took.
  • Makes cause and effect over time easy to follow.
Best forHistory, incidents, rollouts
Avoid whenUnordered facts
FormatsHTML · Markdown table · Mermaid timeline

Example: An illustrative rollout: launch, a viral link overloads the DB, caching and a queue are added.

Day 0Launch with DB only
Week 3Viral link: DB read spike
Week 3Redis cache for hot links added
Month 2Click events moved to a queue
How to read it
  • Read top to bottom (earliest first).
  • Red dots mark problems, green dots mark fixes.
Notes on this example
  • Dots in time order; red = problem, green = fix.
  • Illustrative rollout history.

How to build it: HTML list with a left border and dots. Markdown: a table (time · event) or Mermaid timeline.

3 · Compare & decide

Comparison and decision techniques

In 10 secondsMake trade-offs visible and turn rules into answers.

Comparison matrix

What it is: A table with the options as columns and the comparison criteria as rows.

What it does for the reader

  • Puts options side by side on exactly the same questions.
  • Makes the deciding difference jump out.
Best for2–5 options against the same criteria
Avoid whenOne option — use pros/cons
FormatsAll formats

Example: Three ways to generate short codes compared on collisions, coordination and predictability.

Hash + 7 charsCounter + base62Key service
CollisionsPossible — checkNoneNone
CoordinationNoneDistributed counterExtra service
Predictable IDsNoYesNo
How to read it
  • Pick the criterion you care about most (a row) and read across.

How to build it: A plain table. Keep to 2–5 options.

Pros / cons / use when / avoid when

What it is: Four small boxes that sum up one option: its advantages, its costs, when to pick it, and when not to.

What it does for the reader

  • Turns 'what is it' into 'should I use it'.
  • Forces balanced coverage — every option gets its downsides.
Best forEvery single option or strategy
Avoid whenNever skip it for a choice
FormatsAll formats (Markdown: 4-column table)

Example: The key-service option for generating short codes.

Pros
  • No collisions
  • Batches keep it fast
Cons
  • One more service
Use when
  • High write volume
Avoid when
  • Tiny scale
How to read it
  • Green = benefits, red = costs.
  • 'Use when' and 'Avoid when' are the practical decision rules.

How to build it: A 4-column grid. Markdown: a 4-column table.

2×2 quadrant

What it is: A square split into four boxes by two axes, with options placed as dots according to how they score on each axis.

What it does for the reader

  • Compares options on two criteria at once.
  • Names the four situations (e.g. cheap and safe vs costly and risky).
Best forTwo dimensions that matter at once
Avoid whenMore than two criteria — use a matrix
FormatsHTML/SVG · Mermaid quadrantChart

Example: Code-generation options placed by collision risk and operating cost; bottom-left is best.

How to read it
  • Find each dot: left–right is the first criterion, bottom–top the second.
  • The quadrant labels tell you what that corner means.
Notes on this example
  • Bottom-left is the ideal corner here (cheap and safe).
  • Illustrative placement; the axes are the argument.

How to build it: SVG square with two dividing lines and labelled dots. Markdown: Mermaid quadrantChart.

Decision wizard / tree

What it is: A short series of yes/no questions that ends in a recommendation.

What it does for the reader

  • Turns rules of thumb into a direct answer for the reader's situation.
  • Shows which factor decides the choice.
Best forRules that lead to a recommendation
Avoid whenJudgement calls with no clear rules
FormatsHTML · React · Mermaid flowchart TD

Example: Choosing between a DB sequence, a distributed counter and a key service.

How to read it
  • Answer each question honestly; the first matching rule gives the result.
  • Start again to explore other answers.
Notes on this example
  • Answer yes/no; the first matching rule gives the result.
  • Static version: a decision tree in Mermaid flowchart TD.

How to build it: HTML: questions in a list with yes/no targets and a results map. Markdown: Mermaid flowchart TD with diamond decision nodes.

Myth / reality

What it is: A two-column table pairing a common wrong belief with the correct version.

What it does for the reader

  • Corrects misconceptions directly instead of hoping readers notice.
  • Great for topics where intuition is wrong.
Best forCorrecting common misconceptions
Avoid whenNo real misconception exists
FormatsAll formats

Example: Two common misconceptions about redirects and hashing.

MythReality
301 is always better — it's permanent301 is cached by browsers, so you lose repeat-click analytics; 302 keeps them
Hashing the URL avoids a key service for freeCollisions still need checks at 3.5 trillion keys
How to read it
  • Left column: what people often think. Right column: what is actually true and why.

How to build it: A plain 2-column table.

Before / after

What it is: Two panels side by side showing a situation before and after a change.

What it does for the reader

  • Makes the effect of a fix or design change concrete.
  • Shows the size of the improvement.
Best forShowing an improvement or fix
Avoid whenThe difference is invisible side by side
FormatsAll formats

Example: Redirect traffic before and after adding a Redis cache.

Before
Every redirect → KV store
20,000 reads/s at peak hit the DB
After
Hot links → Redis
~80% of reads never reach the DB
How to read it
  • Compare the same line in both panels; the difference is the point.

How to build it: Two boxes tagged red/green. Markdown: two short code blocks or a 3-column table (aspect · before · after).

Number techniques

In 10 secondsMake numbers checkable and let readers play with assumptions.

Ladder table (+ slider)

What it is: A table where each row is one value of a setting and shows what that value causes; the slider lets readers try values in between.

What it does for the reader

  • Shows how a setting's effect changes across its range.
  • Helps pick a sensible value instead of guessing.
Best forA parameter with a range of values
Avoid whenA single value
FormatsHTML/SVG · React · Mermaid

Example: How many keys each short-code length gives, and how long that lasts at 100M links a month.

Code length (base62)Keys availableEnough for 100M/month for…
5≈ 916 million≈ 9 months
6≈ 56.8 billion≈ 47 years
7≈ 3.5 trillion≈ 2,900 years

How to read it
  • Each row = one setting value → its consequence.
  • Move the slider to recompute the result live.
Notes on this example
  • Each row is one setting with its consequence.
  • The slider recomputes 62^n live.

How to build it: A table plus a range input that recomputes the formula. Markdown: the table only.

Calculator (formula shown)

What it is: Input boxes with the key assumptions, plus a block that shows the formula and the result step by step.

What it does for the reader

  • Lets readers test their own numbers.
  • Builds trust: every step of the arithmetic is visible.
Best forSizing, cost, capacity
Avoid whenThe numbers aren't in the source — never invent inputs
FormatsHTML · React (Markdown: worked arithmetic)

Example: Storage and write-rate estimates from URLs per month, record size and years.

How to read it
  • Change an input; the formula block updates.
  • Defaults are the numbers from the source.
Notes on this example
  • Inputs default to the source's numbers.
  • The formula block shows every step so readers can re-check.
How to build it: Number inputs + a pre block rebuilt on input. Markdown: worked arithmetic in a code block.

5 · Explain
Explanation techniques
In 10 secondsMake one idea concrete: annotate it, dramatise it, compare it to something familiar.
Annotated code
What it is: A short code snippet with comments on the lines that matter.
What it does for the reader
  • Shows exactly how an idea is implemented.
  • Comments explain why, not just what.
Best forImplementation details
Avoid whenPseudocode pretending to be real — mark it
FormatsAll formats
Example: Encoding a number in base62 to make a short code.
# Illustrative: base62 encode a counter value
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
def base62(n: int) -> str:
    s = ""
    while n:
        n, r = divmod(n, 62)      # take one base-62 digit
        s = ALPHABET[r] + s
    return s or "0"
How to read it
  • Read the comments first, then the code they point at.
  • 'Illustrative' means written for the guide, not taken from the source.
How to build it: A pre block with comment spans. Markdown: a fenced code block.
Highlighted anatomy
What it is: One real artefact (a URL, prompt, config line) with each part coloured and a legend explaining the colours.
What it does for the reader
  • Shows the structure hidden inside something that looks like one string.
  • Teaches the name of each part.
Best forShowing the parts of one artefact (URL, prompt, config)
Avoid whenThe artefact has no meaningful parts
FormatsHTML · Markdown (bold/code)
Example: The parts of a short URL: domain, short code, optional tracking.
scheme + domainshort codeoptional tracking
https://sho.rt/aB3xK9q?utm_source=mail
How to read it
  • Match each coloured part to the legend above it.
Notes on this example
  • Colours map to the legend above the box.
  • Illustrative URL.
How to build it: Coloured spans with a legend. Markdown: bold/code for each part with a list explaining them.
Chat mock with toggle
What it is: A fake chat conversation showing how a bot or model answers, with a switch that changes one condition.
What it does for the reader
  • Shows behaviour, not just rules.
  • The toggle proves what one change (a prompt line, a setting) does.
Best forBehaviour of a bot or model
Avoid whenStatic facts
FormatsHTML/SVG · React · Mermaid
Example: A model answering 'use 301?' with and without a design rule about analytics.
How to read it
  • Read the conversation, then flip the toggle and compare the answer.
Notes on this example
  • Toggle to see how one line changes the answer.
  • Illustrative.
How to build it: Chat bubbles + a checkbox that swaps the answer. Markdown: two short transcripts (before / after).
Analogy card
What it is: A comparison with something familiar from everyday life, plus where the comparison stops working.
What it does for the reader
  • Gives beginners a mental model fast.
  • Stating where it breaks prevents wrong conclusions.
Best forAbstract ideas
Avoid whenThe analogy breaks exactly where it matters
FormatsAll formats
Example: A short link as a coat-check ticket.
A short link is a coat-check ticket.
  • You hand over a long URL (coat), get a short code (ticket).
  • Anyone with the ticket gets the coat back.
  • Where it breaks: tickets are reused after pickup; short codes must never be reused.
How to read it
  • Read the analogy, then the 'where it breaks' line — that is the part experts care about.
How to build it: A box with the analogy in bold and 2–3 bullets. Markdown: the same as a quote plus bullets.
Fishbone / 5 whys
What it is: A root-cause diagram shaped like a fish skeleton: the problem is the head, and each bone is a category of possible causes.
What it does for the reader
  • Organises many possible causes so none are forgotten.
  • Separates symptoms from root causes.
Best forRoot causes
Avoid whenOnly one cause — just say it
FormatsHTML/SVG · React · Mermaid
Example: Possible causes of slow redirects at peak.
How to read it
  • The box on the right is the problem.
  • Each bone is a cause category (e.g. cache, database); the small text is a specific cause.
Notes on this example
  • Spine points to the effect; each bone is a cause category.
  • Illustrative causes for slow redirects.
How to build it: SVG spine with angled bones. Markdown: a table (category · cause) or a 5-whys chain in Mermaid flowchart TD.
Layer pipeline
What it is: A stack of checks something must pass in order, where each layer shows whether it passed, stopped it, or was never reached.
What it does for the reader
  • Shows defence in depth: several checks, each catching different problems.
  • Shows why cheap checks go first.
Best forChecks something passes through
Avoid whenOne check
FormatsHTML/SVG · React · Mermaid
Example: What happens to a normal URL, a javascript: URL, a phishing link and a bot when they try to create short links.
How to read it
  • Pick a scenario from the list.
  • Green = passed, red = stopped here, faded = never reached.
Notes on this example
  • Green passes, red stops, faded never reached.
  • Early layers are cheap; order them first.
How to build it: HTML rows coloured by state per scenario. Markdown: a table (scenario × layer).
