# Engineering ledger

A flat `decisions/` directory is fine at 10 records and unusable at 300. Nobody
browses it, so nobody reads it, so writing to it stops paying — and the whole
discipline quietly dies. Three mechanisms prevent that.

## Trigger

**Fire when:** you need to know why something is the way it is; you added a record;
you want to check whether a spec, PRD or fix has its reasoning recorded; a records
directory has grown large.

**Do not fire when:** you are mid-implementation and the question is "what does this
code do" — that is `codebase-comprehension`.

## The scheme

```
prds/<feature>/prd.md          why we are building it
specs/<feature>/spec.md        what we are building
decisions/ADR-NNNN-slug.md     why it is built this way
rca/RCA-NNNN-slug.md           why it broke
reviews/REV-NNNN-slug.md       what a review concluded
ledger/INDEX.md                generated: every record, by type
ledger/MAP.md                  generated: the traceability matrix
```

**1. Typed, prefixed, monotonic ids.** `ADR-0007`, `RCA-0002`. The id is in the
filename, so it is greppable, and a link to it survives the file moving.

**2. Date sharding at a threshold.** Past 40 records in one directory, `ledger.py
shard` moves them to `decisions/YYYY/QN/` and writes a per-shard index. The master
index links to shards instead of listing 300 rows. **Ids do not change**, so nothing
that referenced a record breaks.

**3. A traceability matrix**, because the question people actually ask is not "what
records exist" but "is there a decision behind this spec?" `ledger/MAP.md` is a
feature × record-type grid, and `ledger.py gaps` reports the missing cells that
matter.

## Rules

1. Record at the moment of the decision, not later. Reasoning evaporates within days.
   *Enforced by:* `python3 scripts/decide.py new` / `scripts/rca.py new`

2. Every record needs a stable id and a date. Both come from the scaffolding tools —
   do not hand-create record files.
   *Enforced by:* `python3 scripts/ledger.py index` (records without a parseable id
   surface as unattached)

3. Attach every record to a feature, via `links.feature`, a tag matching a spec
   directory, or an `affects` glob. An unattached record is findable by id and
   invisible by feature.
   *Enforced by:* `python3 scripts/ledger.py map` lists unattached records separately

4. Never hand-edit a generated index. `ledger/INDEX.md` and `ledger/MAP.md` are
   outputs.
   *Enforced by:* both files carry a "regenerated by" header; `ledger.py index`
   overwrites them

5. Shard before a directory becomes unbrowsable, not after.
   *Enforced by:* `python3 scripts/ledger.py gaps` warns past 40 records per directory

6. Search the ledger before asking a human or re-deriving an answer.
   *Enforced by:* `python3 scripts/ledger.py find <term>`

7. Run the linkage audit in CI so gaps surface while the context is fresh.
   *Enforced by:* `python3 scripts/ledger.py check`

## Verify

```bash
# regenerate both indexes and audit linkage (this is the CI command)
python3 scripts/ledger.py check

# individually
python3 scripts/ledger.py index      # ledger/INDEX.md — every record by type
python3 scripts/ledger.py map        # ledger/MAP.md  — feature x record-type matrix
python3 scripts/ledger.py gaps       # specs with no decision, PRDs with no spec, ...

# retrieval
python3 scripts/ledger.py find "session"       # across ids, titles and bodies
python3 scripts/decide.py trace src/auth/x.ts  # which decision governs this file
python3 scripts/ledger.py stats                 # volume per month, sharding threshold

# growth management (ids stay stable; links keep working)
python3 scripts/ledger.py shard
```

## Failure modes

This skill rejects:

- **A spec with no decision record.** Either no non-obvious choice was made — say so —
  or the reasoning is undocumented.
- **A PRD with no spec** — nothing turns it into work.
- **An RCA with no linked decision**, when an assumption being violated is one of the
  most common root causes.
- **A decision with no `affects` glob and no linked feature** — unreachable from the
  code it governs, so nobody will ever find it from the place it matters.
- **A record with a malformed meta block**, reported as an ERROR rather than silently
  skipped.
- **40+ records in one flat directory**, which is the point at which browsing stops.
- **A hand-edited index**, which will be overwritten and meanwhile lies.

**Honest limitations:**
- Feature attachment is **inferred** when not explicit: from `links.feature`, then a
  tag matching a spec directory, then the last non-glob segment of an `affects` path.
  That last heuristic is weak — prefer `links.feature`.
- `find` is substring matching over ids, titles and bodies. There is no semantic
  search, so a question phrased differently from the record will not match.
- **Nothing forces a record to exist.** The gate is on quality and linkage, not
  existence. The mitigation is upstream: `plan_feature.py` generates the decision table
  with the choices already listed, so not recording one is a visible omission.

## Scale

`solo`: the index alone, no sharding. The value is that in six months you will not
remember, and `find` beats archaeology.
`small-team (2-10)`: add `gaps` to CI. This is where "is there a decision behind this?"
starts getting asked in review.
`org (10+)`: sharding and the traceability matrix become load-bearing, because the
records outlive the people who wrote them.
